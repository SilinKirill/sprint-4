# Задание 8. Выявление и устранение «горячих» шардов

## 1. Контекст

На категорию «Электроника» приходится около 70% запросов, поэтому один из шардов может стать горячим.

В задании 7 для `products` уже выбран shard key:

```
{ geo_zone: 1, product_id: "hashed" }
```

Он не использует `category` и распределяет товары по хэшу `product_id` внутри геозоны, что снижает риск концентрации популярной категории на одном шарде.

---

## 2. Метрики мониторинга

Метрики собираются с узлов каждого replica set, агрегируются по шарду и сравниваются между шардами.

| Метрика                               | Условие для алерта                                                  |
|---------------------------------------|---------------------------------------------------------------------|
| CPU                                   | Более 80% в течение 10 минут                                        |
| WiredTiger Cache                      | Заполнение более 90% и рост количества вытеснений страниц           |
| Disk I/O и свободное место            | Задержка диска заметно выше остальных шардов или свободно менее 20% |
| Операции чтения и записи в секунду    | Нагрузка более чем в два раза выше среднего по кластеру             |
| p95 и p99 времени выполнения запросов | Задержка более чем в два раза выше среднего по кластеру             |
| Объём данных и количество документов  | Отклонение от среднего по шардам более чем на 20%                   |
| Состояние balancer                    | Balancer выключен или миграции длительное время не выполняются      |
| Доля запросов по категориям           | Одна категория формирует более 50% запросов                         |

Шард считается горячим, если повышенная нагрузка сохраняется не менее 10 минут и подтверждается одновременно ресурсными метриками и количеством операций или задержкой запросов. Указанные пороги являются стартовыми и уточняются после нагрузочного тестирования.

CPU, Disk I/O и свободное место собираются системой инфраструктурного мониторинга. Метрики WiredTiger и операций MongoDB берутся из `serverStatus`, а задержки запросов — из системы мониторинга приложения или MongoDB.

### Команды проверки

Команды выполняются через `mongos`:

```
sh.status()
sh.getShardedDataDistribution()
sh.getBalancerState()
sh.isBalancerRunning()
```

Статистика MongoDB проверяется на узлах replica set каждого шарда:

```
db.serverStatus()
```

## 3. Устранение дисбаланса

### 3.1. Автоматическая балансировка

MongoDB Balancer должен быть постоянно включён:

```
sh.startBalancer()
```

Balancer автоматически переносит диапазоны данных между шардами при неравномерном распределении данных.

Balancer выравнивает размещение данных, но не учитывает количество запросов. Поэтому при равномерном объёме данных и неравномерной нагрузке необходимо проверить shard key и распределение запросов.

### 3.2. Добавление нового шарда

Если текущим шардам не хватает общей мощности, в кластер добавляется новый шард, развёрнутый как отдельный replica set:

```
sh.addShard("shard3/shard3-1:27018")
```

После добавления новый шард участвует в автоматической балансировке, и balancer переносит на него часть диапазонов данных.

### 3.3. Изменение shard key

Для устранения дисбаланса, вызванного shard key, используется resharding. Для коллекции `products` целевой ключ соответствует решению задания 7:

```
db.adminCommand({
  reshardCollection: "mobile_world.products",
  key: {
    geo_zone: 1,
    product_id: "hashed"
  }
})
```

## 4. Реакция на горячий шард

| Причина                                                 | Действие                                              |
|---------------------------------------------------------|-------------------------------------------------------|
| Неравномерно распределены данные                        | Проверить и включить balancer                         |
| Не хватает общей мощности кластера                      | Добавить новый шард                                   |
| Дисбаланс вызван shard key                              | Выполнить `reshardCollection`                         |
| Данные распределены равномерно, но нагрузка различается | Проанализировать популярные товары и профиль запросов |

---

## 5. Вывод

Состояние шардов контролируется по CPU, WiredTiger Cache, дисковой нагрузке, количеству операций, задержкам запросов и распределению данных.

Основной механизм автоматического перераспределения — MongoDB Balancer. При нехватке мощности добавляется новый шард, а при дисбалансе, вызванном неудачным shard key, выполняется resharding. Выбранный в задании 7 ключ `{ geo_zone: 1, product_id: "hashed" }` снижает риск концентрации категории «Электроника» на одном шарде.
