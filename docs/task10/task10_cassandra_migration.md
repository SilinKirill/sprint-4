# Задание 10. Миграция на Cassandra

## 10.1. Выбор данных для переноса

| Данные                                 | Перенос в Cassandra | Обоснование                                                                                                  |
|----------------------------------------|---------------------|--------------------------------------------------------------------------------------------------------------|
| Заказы                                 | Да                  | Критичные данные, высокая интенсивность записи, требуется доступность при отказе отдельных узлов и между ЦОД |
| История заказов                        | Да                  | Последовательная запись событий, чтение по заказу или пользователю, JOIN не требуется                        |
| Активные корзины                       | Да                  | Частые чтения и изменения по пользователю или сессии, небольшой объём данных, поддержка TTL                  |
| Пользовательские сессии                | Да                  | Доступ по `session_id`, высокая нагрузка, короткий срок хранения и TTL                                       |
| Каталог товаров                        | Да                  | Высокая нагрузка на чтение, данные можно денормализовать под карточку товара и поиск по категории            |
| Остатки и итоговая цена перед покупкой | Нет                 | Требуются актуальные значения и атомарное списание остатка. Эти операции остаются в MongoDB                  |

Cassandra подходит выбранным данным благодаря горизонтальному масштабированию, работе в нескольких ЦОД и высокой скорости чтения и записи по известному ключу.

Каталог в Cassandra используется для просмотра товаров. Перед созданием заказа цена и остаток повторно проверяются в MongoDB.

## 10.2. Концептуальная модель

В Cassandra таблицы проектируются под конкретные запросы. Один и тот же объект может храниться в нескольких таблицах в денормализованном виде.

Пример keyspace для двух ЦОД:

```
CREATE KEYSPACE mobile_world
WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'dc1': 3,
  'dc2': 3
};
```

### Итоговые ключи

| Таблица                 | Назначение                   | Partition key                     | Clustering columns       |
|-------------------------|------------------------------|-----------------------------------|--------------------------|
| `product_by_id`         | Карточка товара              | `(product_id, geo_zone)`          | —                        |
| `products_by_category`  | Поиск по категории и цене    | `(geo_zone, category, bucket_id)` | `price`, `product_id`    |
| `order_by_id`           | Текущее состояние заказа     | `order_id`                        | —                        |
| `order_items_by_order`  | Состав заказа                | `order_id`                        | `product_id`             |
| `orders_by_user_month`  | История заказов пользователя | `(user_id, order_month)`          | `created_at`, `order_id` |
| `order_events_by_order` | История изменений заказа     | `order_id`                        | `event_id`               |
| `cart_items_by_owner`   | Активная корзина             | `(owner_type, owner_id)`          | `product_id`             |
| `session_by_id`         | Пользовательская сессия      | `session_id`                      | —                        |

### Каталог товаров

```
CREATE TABLE mobile_world.product_by_id (
  product_id uuid,
  geo_zone text,
  name text,
  category text,
  price decimal,
  attributes map<text, text>,
  PRIMARY KEY ((product_id, geo_zone))
);
```

```
CREATE TABLE mobile_world.products_by_category (
  geo_zone text,
  category text,
  bucket_id tinyint,
  price decimal,
  product_id uuid,
  name text,
  PRIMARY KEY ((geo_zone, category, bucket_id), price, product_id)
)
WITH CLUSTERING ORDER BY (price ASC, product_id ASC);
```

`bucket_id` вычисляется приложением как `hash(product_id) % N`, где количество bucket `N` определяется по результатам нагрузочного тестирования. Это распределяет популярную категорию по нескольким партициям и снижает риск горячей партиции.

### Заказы

```
CREATE TABLE mobile_world.order_by_id (
  order_id uuid PRIMARY KEY,
  user_id uuid,
  geo_zone text,
  created_at timestamp,
  status text,
  total_amount decimal
);
```

```
CREATE TABLE mobile_world.order_items_by_order (
  order_id uuid,
  product_id uuid,
  price decimal,
  quantity int,
  PRIMARY KEY ((order_id), product_id)
);
```

```
CREATE TABLE mobile_world.orders_by_user_month (
  user_id uuid,
  order_month date,
  created_at timestamp,
  order_id uuid,
  status text,
  total_amount decimal,
  PRIMARY KEY ((user_id, order_month), created_at, order_id)
)
WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

```
CREATE TABLE mobile_world.order_events_by_order (
  order_id uuid,
  event_id timeuuid,
  status text,
  details text,
  PRIMARY KEY ((order_id), event_id)
)
WITH CLUSTERING ORDER BY (event_id DESC);
```

`order_month` используется для разбиения истории заказов пользователя по месяцам и предотвращает неограниченный рост одной партиции.

История изменений одного заказа хранится в отдельной партиции с ключом `order_id` и сортируется по `event_id`.

### Активные корзины

Пользовательские и гостевые корзины хранятся в одной таблице. Владелец корзины определяется полями `owner_type` и `owner_id`: для пользователя используются значения `user` и `user_id`, для гостя — `session` и `session_id`.

Составной partition key `(owner_type, owner_id)` группирует все товары одной корзины в одной партиции, а `product_id` различает товары внутри неё.

```
CREATE TABLE mobile_world.cart_items_by_owner (
  owner_type text,
  owner_id text,
  product_id uuid,
  quantity int,
  updated_at timestamp,
  PRIMARY KEY ((owner_type, owner_id), product_id)
);
```

TTL ограничивает срок хранения корзины. Его значение определяется бизнес-требованиями.

### Пользовательские сессии

```
CREATE TABLE mobile_world.session_by_id (
  session_id text PRIMARY KEY,
  user_id uuid,
  created_at timestamp,
  payload text
)
WITH default_time_to_live = 86400;
```

В примере TTL сессии составляет 24 часа; фактическое значение определяется бизнес-требованиями.

### Предотвращение горячих партиций

| Риск                              | Решение                                       |
|-----------------------------------|-----------------------------------------------|
| Популярная категория товаров      | Разделение по `bucket_id`                     |
| Рост истории заказов пользователя | Разделение по `order_month`                   |
| Общая горячая партиция корзин     | Отдельная партиция на пользователя или сессию |
| Накопление корзин и сессий        | TTL                                           |

При добавлении узлов Cassandra перераспределяет только соответствующие диапазоны токенов, а не все данные кластера.

## 10.3. Репликация и восстановление согласованности

При факторе репликации 3 в локальном ЦОД:

- `LOCAL_QUORUM` ожидает подтверждение двух из трёх реплик;
- `LOCAL_ONE` ожидает ответ одной реплики и обеспечивает меньшую latency, но допускает чтение отстающей версии.

### Consistency Level

| Данные                    | Запись         | Чтение         | Обоснование                                                                                                       |
|---------------------------|----------------|----------------|-------------------------------------------------------------------------------------------------------------------|
| Текущее состояние заказа  | `LOCAL_QUORUM` | `LOCAL_QUORUM` | После изменения должен читаться актуальный статус                                                                 |
| История заказов и событий | `LOCAL_QUORUM` | `LOCAL_ONE`    | Для записи требуется подтверждение большинства реплик, но при чтении допустимо кратковременное отставание истории |
| Активная корзина          | `LOCAL_QUORUM` | `LOCAL_QUORUM` | Пользователь должен сразу видеть изменения корзины                                                                |
| Пользовательская сессия   | `LOCAL_QUORUM` | `LOCAL_QUORUM` | Изменение и завершение сессии должны сразу учитываться                                                            |
| Каталог товаров           | `LOCAL_QUORUM` | `LOCAL_ONE`    | Для просмотра допустима временно устаревшая версия; перед покупкой данные проверяются в MongoDB                   |

### Выбранные стратегии восстановления

| Данные                    | Выбранные стратегии                                | Обоснование                                                                                 |
|---------------------------|----------------------------------------------------|---------------------------------------------------------------------------------------------|
| Текущее состояние заказа  | Hinted Handoff + Read Repair + Anti-Entropy Repair | Данные критичны, часто читаются и должны сохраняться длительное время                       |
| История заказов и событий | Hinted Handoff + Anti-Entropy Repair               | История долгоживущая, но читается реже, поэтому Read Repair не является основным механизмом |
| Активные корзины          | Hinted Handoff + Read Repair                       | Корзины часто читаются и изменяются, но хранятся недолго                                    |
| Пользовательские сессии   | Hinted Handoff + Read Repair                       | Сессии часто читаются, быстро изменяются и удаляются по TTL                                 |
| Каталог товаров           | Hinted Handoff + Anti-Entropy Repair               | Кратковременное отставание допустимо, а данные хранятся длительно                           |

Hinted Handoff используется для восстановления после кратковременных сбоев, Read Repair — для исправления расхождений в часто читаемых данных, Anti-Entropy Repair — для периодической сверки и синхронизации долгоживущих данных, включая расхождения, не устранённые другими механизмами.

## Вывод

В Cassandra переносятся заказы, история заказов, активные корзины, пользовательские сессии и каталог товаров. Остатки и итоговая цена перед покупкой остаются в MongoDB.

Partition key выбраны под основные запросы, а clustering columns задают сортировку внутри партиций. Bucket-разбиение категорий и разделение истории по месяцам предотвращают горячие и неограниченно растущие партиции.

`LOCAL_QUORUM` применяется для данных, где требуется актуальное состояние, а `LOCAL_ONE` — для каталога и истории, где допустимо кратковременное отставание. Для восстановления используются Hinted Handoff, Read Repair и Anti-Entropy Repair в зависимости от характера данных.
