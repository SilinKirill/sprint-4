# Задание 7. Проектирование схем коллекций для шардирования данных

## 1. Итоговое решение

| Коллекция  | Стратегия                                     | Shard key                               |
|------------|-----------------------------------------------|-----------------------------------------|
| `products` | Геошардинг + хэшированное шардирование        | `{ geo_zone: 1, product_id: "hashed" }` |
| `orders`   | Геошардинг + хэшированное шардирование        | `{ geo_zone: 1, user_id: "hashed" }`    |
| `carts`    | Хэшированное шардирование по составному ключу | `{ user_id: "hashed", session_id: 1 }`  |

---

## 2. Коллекция `products`

### 2.1. Схема документа

```
{
  _id: ObjectId,
  product_id: ObjectId,
  geo_zone: String,
  name: String,
  category: String,
  price: Decimal128,
  stock: NumberInt,
  attributes: {
    color: String,
    size: String
  }
}
```

Один документ хранит товар и его остаток в конкретной геозоне.

### 2.2. Кандидаты на shard key

- `product_id`;
- `geo_zone + product_id`.

### 2.3. Выбранное шардирование

Используется геошардинг в сочетании с хэшированным шардированием. `geo_zone` локализует данные по регионам, а хэшированный `product_id` равномерно распределяет товары внутри геозоны.

### 2.4. Shard key

```
{ geo_zone: 1, product_id: "hashed" }
```

```
sh.shardCollection(
  "mobile_world.products",
  { geo_zone: 1, product_id: "hashed" }
)
```

### 2.5. Основные операции

#### Обновление остатка

Ключ поиска:

```
{
  geo_zone,
  product_id
}
```

```
db.products.updateOne(
  {
    geo_zone: "ekaterinburg",
    product_id: ObjectId("65f000000000000000000001"),
    stock: { $gte: 1 }
  },
  {
    $inc: { stock: -1 }
  }
)
```

#### Поиск товаров по категории и диапазону цен

Ключ поиска:

```
{
  geo_zone,
  category,
  price
}
```

```
db.products.find({
  geo_zone: "ekaterinburg",
  category: "electronics",
  price: {
    $gte: Decimal128("10000.00"),
    $lte: Decimal128("100000.00")
  }
})
```

#### Получение описания товара

Ключ поиска:

```
{
  geo_zone,
  product_id
}
```

```
db.products.findOne({
  geo_zone: "ekaterinburg",
  product_id: ObjectId("65f000000000000000000001")
})
```

### 2.6. Индексы

```
db.products.createIndex({
  geo_zone: 1,
  category: 1,
  price: 1
})
```

Назначение: поиск товаров в геозоне по категории и диапазону цен.

---

## 3. Коллекция `orders`

### 3.1. Схема документа

```
{
  _id: ObjectId,
  user_id: ObjectId,
  created_at: Date,
  items: [
    {
      product_id: ObjectId,
      price: Decimal128
    }
  ],
  status: String,
  total_amount: Decimal128,
  geo_zone: String
}
```

### 3.2. Кандидаты на shard key

- `user_id`;
- `geo_zone + user_id`.

### 3.3. Выбранное шардирование

Используется геошардинг в сочетании с хэшированным шардированием. `geo_zone` локализует заказы по регионам, а хэшированный `user_id` равномерно распределяет пользователей внутри геозоны.

### 3.4. Shard key

```
{ geo_zone: 1, user_id: "hashed" }
```

```
sh.shardCollection(
  "mobile_world.orders",
  { geo_zone: 1, user_id: "hashed" }
)
```

### 3.5. Основные операции

#### Создание заказа

Ключ распределения:

```
{
  geo_zone,
  user_id
}
```

```
db.orders.insertOne({
  user_id: ObjectId("64f000000000000000000001"),
  created_at: new Date(),
  items: [
    {
      product_id: ObjectId("65f000000000000000000001"),
      price: Decimal128("79990.00")
    }
  ],
  status: "created",
  total_amount: Decimal128("79990.00"),
  geo_zone: "moscow"
})
```

#### Поиск истории заказов пользователя

Ключ поиска:

```
{
  geo_zone,
  user_id
}
```

```
db.orders.find({
  geo_zone: "moscow",
  user_id: ObjectId("64f000000000000000000001")
})
.sort({
  created_at: -1
})
```

#### Получение статуса заказа

Ключ поиска:

```
{
  geo_zone,
  user_id,
  _id
}
```

```
db.orders.findOne(
  {
    geo_zone: "moscow",
    user_id: ObjectId("64f000000000000000000001"),
    _id: ObjectId("66b000000000000000000001")
  },
  {
    status: 1
  }
)
```

### 3.6. Индексы

```
db.orders.createIndex({
  geo_zone: 1,
  user_id: 1,
  created_at: -1
})
```

Назначение: поиск истории заказов пользователя с сортировкой по дате.

## 4. Коллекция `carts`

### 4.1. Схема документа

```
{
  _id: ObjectId,
  user_id: ObjectId | null,
  session_id: String | null,
  items: [
    {
      product_id: ObjectId,
      quantity: NumberInt
    }
  ],
  status: "active" | "ordered" | "abandoned",
  created_at: Date,
  updated_at: Date,
  expires_at: Date
}
```

### 4.2. Кандидаты на shard key

- `user_id`;
- `session_id`;
- `user_id + session_id`.

### 4.3. Выбранное шардирование

Используется хэшированное шардирование по составному ключу из `user_id` и `session_id`. Ключ поддерживает поиск как пользовательских, так и гостевых корзин без добавления отдельного технического поля.

### 4.4. Shard key

```
{ user_id: "hashed", session_id: 1 }
```

```
sh.shardCollection(
  "mobile_world.carts",
  { user_id: "hashed", session_id: 1 }
)
```

### 4.5. Основные операции

#### Создание пользовательской корзины

Ключ распределения:

```
{
  user_id,
  session_id: null
}
```

```
db.carts.insertOne({
  user_id: ObjectId("64f000000000000000000001"),
  session_id: null,
  items: [],
  status: "active",
  created_at: new Date(),
  updated_at: new Date(),
  expires_at: ISODate("2026-08-24T10:00:00Z")
})
```

#### Создание гостевой корзины

Ключ распределения:

```
{
  user_id: null,
  session_id
}
```

```
db.carts.insertOne({
  user_id: null,
  session_id: "guest-session-123",
  items: [],
  status: "active",
  created_at: new Date(),
  updated_at: new Date(),
  expires_at: ISODate("2026-08-01T10:00:00Z")
})
```

#### Получение активной пользовательской корзины

Ключ поиска:

```
{
  user_id,
  session_id: null,
  status: "active"
}
```

```
db.carts.findOne({
  user_id: ObjectId("64f000000000000000000001"),
  session_id: null,
  status: "active"
})
```

#### Получение активной гостевой корзины

Ключ поиска:

```
{
  user_id: null,
  session_id,
  status: "active"
}
```

```
db.carts.findOne({
  user_id: null,
  session_id: "guest-session-123",
  status: "active"
})
```

#### Добавление товара

```
db.carts.updateOne(
  {
    user_id: ObjectId("64f000000000000000000001"),
    session_id: null,
    status: "active"
  },
  {
    $push: {
      items: {
        product_id: ObjectId("65f000000000000000000001"),
        quantity: NumberInt(1)
      }
    },
    $set: {
      updated_at: new Date()
    }
  }
)
```

#### Замена количества товара

```
db.carts.updateOne(
  {
    user_id: ObjectId("64f000000000000000000001"),
    session_id: null,
    status: "active",
    "items.product_id": ObjectId("65f000000000000000000001")
  },
  {
    $set: {
      "items.$.quantity": NumberInt(3),
      updated_at: new Date()
    }
  }
)
```

#### Удаление товара

```
db.carts.updateOne(
  {
    user_id: ObjectId("64f000000000000000000001"),
    session_id: null,
    status: "active"
  },
  {
    $pull: {
      items: {
        product_id: ObjectId("65f000000000000000000001")
      }
    },
    $set: {
      updated_at: new Date()
    }
  }
)
```

#### Слияние гостевой и пользовательской корзин

Гостевая корзина:

```
{
  user_id: null,
  session_id,
  status: "active"
}
```

Пользовательская корзина:

```
{
  user_id,
  session_id: null,
  status: "active"
}
```

После переноса товаров гостевая корзина помечается как `abandoned`:

```
db.carts.updateOne(
  {
    user_id: null,
    session_id: "guest-session-123",
    status: "active"
  },
  {
    $set: {
      status: "abandoned",
      updated_at: new Date()
    }
  }
)
```

#### Отметка корзины как заказанной

```
db.carts.updateOne(
  {
    user_id: ObjectId("64f000000000000000000001"),
    session_id: null,
    status: "active"
  },
  {
    $set: {
      status: "ordered",
      updated_at: new Date()
    }
  }
)
```

### 4.6. Индексы

```
db.carts.createIndex({
  user_id: 1,
  session_id: 1,
  status: 1
})
```

Назначение: получение активной пользовательской или гостевой корзины.

```
db.carts.createIndex(
  { expires_at: 1 },
  { expireAfterSeconds: 0 }
)
```

Назначение: автоматическое удаление устаревших корзин.

---

## 5. Вывод

Для коллекций `products` и `orders` выбрано сочетание географического и хэшированного шардирования. Поле `geo_zone` группирует данные по регионам, а хэшированный идентификатор равномерно распределяет нагрузку внутри каждой геозоны.

Для коллекции `carts` используется составной shard key `{ user_id: "hashed", session_id: 1 }`, который позволяет работать как с пользовательскими, так и с гостевыми корзинами. `user_id` обеспечивает равномерное распределение пользовательских корзин, а `session_id` различает гостевые корзины, у которых `user_id` равен `null`.

# Задание 8. Выявление и устранение «горячих» шардов

## 1. Контекст

На категорию «Электроника» приходится около 70% запросов, поэтому один из шардов может стать горячим.

В задании 7 для `products` уже выбран shard key:

```
{ geo_zone: 1, product_id: "hashed" }
```

Он не использует `category` и распределяет товары по хэшу `product_id` внутри геозоны, что снижает риск концентрации популярной категории на одном шарде.

---

## 2. Метрики мониторинга

Метрики собираются с узлов каждого replica set, агрегируются по шарду и сравниваются между шардами.

| Метрика                               | Условие для алерта                                                  |
|---------------------------------------|---------------------------------------------------------------------|
| CPU                                   | Более 80% в течение 10 минут                                        |
| WiredTiger Cache                      | Заполнение более 90% и рост количества вытеснений страниц           |
| Disk I/O и свободное место            | Задержка диска заметно выше остальных шардов или свободно менее 20% |
| Операции чтения и записи в секунду    | Нагрузка более чем в два раза выше среднего по кластеру             |
| p95 и p99 времени выполнения запросов | Задержка более чем в два раза выше среднего по кластеру             |
| Объём данных и количество документов  | Отклонение от среднего по шардам более чем на 20%                   |
| Состояние balancer                    | Balancer выключен или миграции длительное время не выполняются      |
| Доля запросов по категориям           | Одна категория формирует более 50% запросов                         |

Шард считается горячим, если повышенная нагрузка сохраняется не менее 10 минут и подтверждается одновременно ресурсными метриками и количеством операций или задержкой запросов. Указанные пороги являются стартовыми и уточняются после нагрузочного тестирования.

CPU, Disk I/O и свободное место собираются системой инфраструктурного мониторинга. Метрики WiredTiger и операций MongoDB берутся из `serverStatus`, а задержки запросов — из системы мониторинга приложения или MongoDB.

### Команды проверки

Команды выполняются через `mongos`:

```
sh.status()
sh.getShardedDataDistribution()
sh.getBalancerState()
sh.isBalancerRunning()
```

Статистика MongoDB проверяется на узлах replica set каждого шарда:

```
db.serverStatus()
```

---

## 3. Устранение дисбаланса

### 3.1. Автоматическая балансировка

MongoDB Balancer должен быть постоянно включён:

```
sh.startBalancer()
```

Balancer автоматически переносит диапазоны данных между шардами при неравномерном распределении данных.

Balancer выравнивает размещение данных, но не учитывает количество запросов. Поэтому при равномерном объёме данных и неравномерной нагрузке необходимо проверить shard key и распределение запросов.

### 3.2. Добавление нового шарда

Если текущим шардам не хватает общей мощности, в кластер добавляется новый шард, развёрнутый как отдельный replica set:

```
sh.addShard("shard3/shard3-1:27018")
```

После добавления новый шард участвует в автоматической балансировке, и balancer переносит на него часть диапазонов данных.

### 3.3. Изменение shard key

Для устранения дисбаланса, вызванного shard key, используется resharding. Для коллекции `products` целевой ключ соответствует решению задания 7:

```
db.adminCommand({
  reshardCollection: "mobile_world.products",
  key: {
    geo_zone: 1,
    product_id: "hashed"
  }
})
```

---

## 4. Реакция на горячий шард

| Причина                                                 | Действие                                              |
|---------------------------------------------------------|-------------------------------------------------------|
| Неравномерно распределены данные                        | Проверить и включить balancer                         |
| Не хватает общей мощности кластера                      | Добавить новый шард                                   |
| Дисбаланс вызван shard key                              | Выполнить `reshardCollection`                         |
| Данные распределены равномерно, но нагрузка различается | Проанализировать популярные товары и профиль запросов |

---

## 5. Вывод

Состояние шардов контролируется по CPU, WiredTiger Cache, дисковой нагрузке, количеству операций, задержкам запросов и распределению данных.

Основной механизм автоматического перераспределения — MongoDB Balancer. При нехватке мощности добавляется новый шард, а при дисбалансе, вызванном неудачным shard key, выполняется resharding. Выбранный в задании 7 ключ `{ geo_zone: 1, product_id: "hashed" }` снижает риск концентрации категории «Электроника» на одном шарде.

# Задание 9. Настройка чтения с реплик и консистентность

## 1. Контекст

Каждый шард MongoDB развёрнут как replica set с одним primary и двумя secondary. Запись выполняется на primary, а данные асинхронно копируются на secondary.

Чтение на secondary используется только для операций, где допустимо кратковременное отставание данных. Операции, требующие актуального состояния или чтения сразу после записи, выполняются с primary.

---

## 2. Коллекция `products`

| Операция чтения                                  | Узел      | Допустимая задержка | Обоснование                                                                                                                |
|--------------------------------------------------|-----------|--------------------:|----------------------------------------------------------------------------------------------------------------------------|
| Поиск товаров по категории и диапазону цен       | Secondary |         До 5 секунд | Каталог часто читается. Кратковременное отставание допустимо, так как актуальные цена и остаток проверяются перед покупкой |
| Получение описания товара                        | Secondary |         До 5 секунд | Название, категория и дополнительные атрибуты изменяются редко                                                             |
| Проверка цены и остатка перед оформлением заказа | Primary   |      Не допускается | Устаревшие данные могут привести к продаже отсутствующего товара или применению неверной цены                              |

Задержка до 5 секунд выбрана как допустимый бизнес-порог для просмотра каталога: она позволяет разгрузить primary, но не должна быть заметна пользователю. Перед созданием заказа цена и остаток обязательно повторно читаются с primary.

---

## 3. Коллекция `orders`

| Операция чтения                             | Узел      | Допустимая задержка | Обоснование                                                        |
|---------------------------------------------|-----------|--------------------:|--------------------------------------------------------------------|
| Просмотр истории ранее созданных заказов    | Secondary |         До 5 секунд | История преимущественно читается, а небольшое отставание допустимо |
| Получение только что созданного заказа      | Primary   |      Не допускается | Пользователь должен сразу увидеть результат оформления             |
| Получение текущего статуса и деталей заказа | Primary   |      Не допускается | Статус, состав и сумма должны соответствовать последнему изменению |

Чтение истории сразу после создания или изменения заказа также выполняется с primary. После завершения операции и допустимого интервала историю можно читать на secondary.

---

## 4. Коллекция `carts`

| Операция чтения                             | Узел    | Допустимая задержка | Обоснование                                                                         |
|---------------------------------------------|---------|--------------------:|-------------------------------------------------------------------------------------|
| Получение активной пользовательской корзины | Primary |      Не допускается | Состав корзины часто изменяется, поэтому пользователь должен сразу видеть результат |
| Получение активной гостевой корзины         | Primary |      Не допускается | Требуется актуальное состояние после добавления или удаления товара                 |
| Чтение корзин при слиянии                   | Primary |      Не допускается | Устаревшие данные могут привести к потере или дублированию товаров                  |
| Проверка корзины перед созданием заказа     | Primary |      Не допускается | Состав и количество товаров должны быть актуальными                                 |

Для `carts` secondary не используются для штатного чтения. Они обеспечивают хранение копий данных и автоматическое переключение: при недоступности primary одна из secondary может быть выбрана новым primary.

---

## 5. Контроль задержки репликации

Допустимые 5 секунд — бизнес-требование для запросов чтения, направляемых на secondary. Фактическая задержка репликации должна контролироваться системой мониторинга.

Для ручной проверки состояния secondary:

```
rs.printSecondaryReplicationInfo()
```

Если задержка превышает допустимое значение, запросы чтения временно направляются на primary до восстановления репликации.

Режим чтения задаётся в приложении отдельно для каждой операции:

- `primary` — для чтений, требующих актуальных данных;
- `secondaryPreferred` — для чтений, которым разрешено использовать secondary с возвратом на primary, если secondary недоступны.

---

## 6. Итоговое решение

| Коллекция  | Secondary                           | Primary                                             |
|------------|-------------------------------------|-----------------------------------------------------|
| `products` | Каталог и описание товара           | Актуальные цена и остаток перед покупкой            |
| `orders`   | История ранее созданных заказов     | Только что созданный заказ, текущий статус и детали |
| `carts`    | Не используется для штатного чтения | Все операции чтения активной корзины                |

---

## 7. Вывод

Secondary используются для операций, где допустимо отставание до 5 секунд: просмотра каталога, описания товаров и истории ранее созданных заказов.

Актуальные цена и остаток, текущий статус заказа и состояние корзины читаются на primary. Для `carts` secondary выполняют прежде всего роль резервных узлов и обеспечивают автоматическое переключение.

# Задание 10. Миграция на Cassandra

## 10.1. Выбор данных для переноса

| Данные                                 | Перенос в Cassandra | Обоснование                                                                                                  |
|----------------------------------------|---------------------|--------------------------------------------------------------------------------------------------------------|
| Заказы                                 | Да                  | Критичные данные, высокая интенсивность записи, требуется доступность при отказе отдельных узлов и между ЦОД |
| История заказов                        | Да                  | Последовательная запись событий, чтение по заказу или пользователю, JOIN не требуется                        |
| Активные корзины                       | Да                  | Частые чтения и изменения по пользователю или сессии, небольшой объём данных, поддержка TTL                  |
| Пользовательские сессии                | Да                  | Доступ по `session_id`, высокая нагрузка, короткий срок хранения и TTL                                       |
| Каталог товаров                        | Да                  | Высокая нагрузка на чтение, данные можно денормализовать под карточку товара и поиск по категории            |
| Остатки и итоговая цена перед покупкой | Нет                 | Требуются актуальные значения и атомарное списание остатка. Эти операции остаются в MongoDB                  |

Cassandra подходит выбранным данным благодаря горизонтальному масштабированию, работе в нескольких ЦОД и высокой скорости чтения и записи по известному ключу.

Каталог в Cassandra используется для просмотра товаров. Перед созданием заказа цена и остаток повторно проверяются в MongoDB.

## 10.2. Концептуальная модель

В Cassandra таблицы проектируются под конкретные запросы. Один и тот же объект может храниться в нескольких таблицах в денормализованном виде.

Пример keyspace для двух ЦОД:

```
CREATE KEYSPACE mobile_world
WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'dc1': 3,
  'dc2': 3
};
```

### Итоговые ключи

| Таблица                 | Назначение                   | Partition key                     | Clustering columns       |
|-------------------------|------------------------------|-----------------------------------|--------------------------|
| `product_by_id`         | Карточка товара              | `(product_id, geo_zone)`          | —                        |
| `products_by_category`  | Поиск по категории и цене    | `(geo_zone, category, bucket_id)` | `price`, `product_id`    |
| `order_by_id`           | Текущее состояние заказа     | `order_id`                        | —                        |
| `order_items_by_order`  | Состав заказа                | `order_id`                        | `product_id`             |
| `orders_by_user_month`  | История заказов пользователя | `(user_id, order_month)`          | `created_at`, `order_id` |
| `order_events_by_order` | История изменений заказа     | `order_id`                        | `event_id`               |
| `cart_items_by_owner`   | Активная корзина             | `(owner_type, owner_id)`          | `product_id`             |
| `session_by_id`         | Пользовательская сессия      | `session_id`                      | —                        |

### Каталог товаров

```
CREATE TABLE mobile_world.product_by_id (
  product_id uuid,
  geo_zone text,
  name text,
  category text,
  price decimal,
  attributes map<text, text>,
  PRIMARY KEY ((product_id, geo_zone))
);
```

```
CREATE TABLE mobile_world.products_by_category (
  geo_zone text,
  category text,
  bucket_id tinyint,
  price decimal,
  product_id uuid,
  name text,
  PRIMARY KEY ((geo_zone, category, bucket_id), price, product_id)
)
WITH CLUSTERING ORDER BY (price ASC, product_id ASC);
```

`bucket_id` вычисляется приложением как `hash(product_id) % N`, где количество bucket `N` определяется по результатам нагрузочного тестирования. Это распределяет популярную категорию по нескольким партициям и снижает риск горячей партиции.

### Заказы

```
CREATE TABLE mobile_world.order_by_id (
  order_id uuid PRIMARY KEY,
  user_id uuid,
  geo_zone text,
  created_at timestamp,
  status text,
  total_amount decimal
);
```

```
CREATE TABLE mobile_world.order_items_by_order (
  order_id uuid,
  product_id uuid,
  price decimal,
  quantity int,
  PRIMARY KEY ((order_id), product_id)
);
```

```
CREATE TABLE mobile_world.orders_by_user_month (
  user_id uuid,
  order_month date,
  created_at timestamp,
  order_id uuid,
  status text,
  total_amount decimal,
  PRIMARY KEY ((user_id, order_month), created_at, order_id)
)
WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

```
CREATE TABLE mobile_world.order_events_by_order (
  order_id uuid,
  event_id timeuuid,
  status text,
  details text,
  PRIMARY KEY ((order_id), event_id)
)
WITH CLUSTERING ORDER BY (event_id DESC);
```

`order_month` используется для разбиения истории заказов пользователя по месяцам и предотвращает неограниченный рост одной партиции.

История изменений одного заказа хранится в отдельной партиции с ключом `order_id` и сортируется по `event_id`.

### Активные корзины

Пользовательские и гостевые корзины хранятся в одной таблице. Владелец корзины определяется полями `owner_type` и `owner_id`: для пользователя используются значения `user` и `user_id`, для гостя — `session` и `session_id`.

Составной partition key `(owner_type, owner_id)` группирует все товары одной корзины в одной партиции, а `product_id` различает товары внутри неё.

```
CREATE TABLE mobile_world.cart_items_by_owner (
  owner_type text,
  owner_id text,
  product_id uuid,
  quantity int,
  updated_at timestamp,
  PRIMARY KEY ((owner_type, owner_id), product_id)
);
```

TTL ограничивает срок хранения корзины. Его значение определяется бизнес-требованиями.

### Пользовательские сессии

```
CREATE TABLE mobile_world.session_by_id (
  session_id text PRIMARY KEY,
  user_id uuid,
  created_at timestamp,
  payload text
)
WITH default_time_to_live = 86400;
```

В примере TTL сессии составляет 24 часа; фактическое значение определяется бизнес-требованиями.

### Предотвращение горячих партиций

| Риск                              | Решение                                       |
|-----------------------------------|-----------------------------------------------|
| Популярная категория товаров      | Разделение по `bucket_id`                     |
| Рост истории заказов пользователя | Разделение по `order_month`                   |
| Общая горячая партиция корзин     | Отдельная партиция на пользователя или сессию |
| Накопление корзин и сессий        | TTL                                           |

При добавлении узлов Cassandra перераспределяет только соответствующие диапазоны токенов, а не все данные кластера.

## 10.3. Репликация и восстановление согласованности

При факторе репликации 3 в локальном ЦОД:

- `LOCAL_QUORUM` ожидает подтверждение двух из трёх реплик;
- `LOCAL_ONE` ожидает ответ одной реплики и обеспечивает меньшую latency, но допускает чтение отстающей версии.

### Consistency Level

| Данные                    | Запись         | Чтение         | Обоснование                                                                                                       |
|---------------------------|----------------|----------------|-------------------------------------------------------------------------------------------------------------------|
| Текущее состояние заказа  | `LOCAL_QUORUM` | `LOCAL_QUORUM` | После изменения должен читаться актуальный статус                                                                 |
| История заказов и событий | `LOCAL_QUORUM` | `LOCAL_ONE`    | Для записи требуется подтверждение большинства реплик, но при чтении допустимо кратковременное отставание истории |
| Активная корзина          | `LOCAL_QUORUM` | `LOCAL_QUORUM` | Пользователь должен сразу видеть изменения корзины                                                                |
| Пользовательская сессия   | `LOCAL_QUORUM` | `LOCAL_QUORUM` | Изменение и завершение сессии должны сразу учитываться                                                            |
| Каталог товаров           | `LOCAL_QUORUM` | `LOCAL_ONE`    | Для просмотра допустима временно устаревшая версия; перед покупкой данные проверяются в MongoDB                   |

### Выбранные стратегии восстановления

| Данные                    | Выбранные стратегии                                | Обоснование                                                                                 |
|---------------------------|----------------------------------------------------|---------------------------------------------------------------------------------------------|
| Текущее состояние заказа  | Hinted Handoff + Read Repair + Anti-Entropy Repair | Данные критичны, часто читаются и должны сохраняться длительное время                       |
| История заказов и событий | Hinted Handoff + Anti-Entropy Repair               | История долгоживущая, но читается реже, поэтому Read Repair не является основным механизмом |
| Активные корзины          | Hinted Handoff + Read Repair                       | Корзины часто читаются и изменяются, но хранятся недолго                                    |
| Пользовательские сессии   | Hinted Handoff + Read Repair                       | Сессии часто читаются, быстро изменяются и удаляются по TTL                                 |
| Каталог товаров           | Hinted Handoff + Anti-Entropy Repair               | Кратковременное отставание допустимо, а данные хранятся длительно                           |

Hinted Handoff используется для восстановления после кратковременных сбоев, Read Repair — для исправления расхождений в часто читаемых данных, Anti-Entropy Repair — для периодической сверки и синхронизации долгоживущих данных, включая расхождения, не устранённые другими механизмами.

## Вывод

В Cassandra переносятся заказы, история заказов, активные корзины, пользовательские сессии и каталог товаров. Остатки и итоговая цена перед покупкой остаются в MongoDB.

Partition key выбраны под основные запросы, а clustering columns задают сортировку внутри партиций. Bucket-разбиение категорий и разделение истории по месяцам предотвращают горячие и неограниченно растущие партиции.

`LOCAL_QUORUM` применяется для данных, где требуется актуальное состояние, а `LOCAL_ONE` — для каталога и истории, где допустимо кратковременное отставание. Для восстановления используются Hinted Handoff, Read Repair и Anti-Entropy Repair в зависимости от характера данных.
